## 最新结论与修正状态

接上显示器和鼠标后，用户实际确认：**看不到光标，但点击有效，UI 有 hover 效果**。随后用户把显示器切换到载板 **HDMI 输出 0**，确认光标可见。两次观察均发生在新库尚未安装时。

源码和日志支持的原因是：经典 WindowManager 的 `InputWindowMonitor::UpdateDisplayInfo()` 构造 `MMI::DisplayInfo` 时漏填了 `rsId`，该聚合字段被初始化为 0。MMI 原样消费此字段并调用 `AttachToDisplay(rsId)`；在不显示画面的 RS 屏幕 0 上创建光标，不会让它出现在实际有画面的 RS 屏幕 1 上。桌面窗口走另一条经过正确映射的挂载路径，鼠标事件的逻辑坐标仍有效，所以点击和 hover 可用。切换到 HDMI 0 恰好掩盖了映射遗漏。不能推广为“丝印 HDMI 编号始终等于 RS ID”。

已在构建机修正 `wmserver/src/input_window_monitor.cpp`：从 `GetScreenInfoByDisplayId()` 查询真实屏幕，填入 `GetRsId()`；screenArea 与 ScreenInfo 使用一致的物理屏幕 ID；屏幕结构体值初始化；窗口信息补填逻辑 `displayId`，消除已定位的 `physical(-1)` 来源。没有有效 RS 屏幕时不发布该条显示信息。相应的无效屏幕单元测试断言已调整。

`libwms.z.so` 已编译、链接成功，SHA256 为 `c7055481c6e72aeedaa39a487af6e6b5f8b84fe5d73090c212e38213db7d56ab`。修改后的单元测试源文件亦编译通过，测试二进制尚未执行。**尚未安装到板上，也未完成新库的 HDMI 1 验收。** 原系统库未替换，原镜像未改写。串口整段传输未通过校验，后续改用分块回执方案；最后两次串口探测均无回显，等待确认板卡状态。不能把源码修正或编译成功写成已上板修复。

先前 `MoveSoft` 补丁保留原状，以避免同时改变多个因素；它所依据的“RS 只记录边界、不更新节点”推论已被本轮读码推翻。

## 前半段实测：尚未接显示器

通过 Windows COM4、1500000 8N1 访问开发板 root 控制台；通过 SSH 访问构建机 `<BUILD_HOST>:<SSH_PORT>` 的 `/home/<user>/ohos/src`。本节取证期间尚未修改产品源码或参数；后续修正情况见上节。本轮未主动重启开发板或服务。

1. 第一次读取 `/proc/bus/input/devices` 时只有 event0～event6。这只能证明读取当时没有已注册的鼠标，不能证明历史上从未接入过鼠标。
2. 用户表示准备接入鼠标后，后续读取发现真实 USB 鼠标：

   ```text
   N: Name="PixArt Dell MS116 USB Optical Mouse"
   I: Bus=0003 Vendor=413c Product=301a Version=0111
   H: Handlers=event7 dmcfreq
   B: REL=903
   ```

   路径为 `usbdrd3_1/fc400000.usb/.../usb3/3-1`。USB 接口 uevent 显示 `DRIVER=usbhid`、`INTERFACE=3/1/2`；`multimodalinput`（本轮 PID 321）已通过 fd 31 打开 `/dev/input/event7`。
3. MMI 日志在真实鼠标操作期间连续出现：

   ```text
   MouseTransformProcessor: [|176]No display
   MouseTransformProcessor: [|524]No display
   InputKeyFlow: PixArt Dell MS116 USB Optical Mouse, ...
   ```

   对照实际源码，176 行是移动处理、524 行是按下处理；两处均在 `WIN_MGR->GetCursorPos().displayId < 0` 时提前返回。这证明事件已进入 MMI，此次阻断发生在取得有效显示目标之前，尚不能归因于光标位置提交或合成。
4. 多次读取内核显示状态，得到：

   ```text
   /sys/class/drm/card0-HDMI-A-1/status: disconnected
   /sys/class/drm/card0-HDMI-A-1/enabled: disabled
   /sys/class/drm/card0-HDMI-A-2/status: disconnected
   /sys/class/drm/card0-HDMI-A-2/enabled: disabled
   /sys/kernel/debug/dri/0/summary:
   Video Port0: DISABLED
   Video Port1: DISABLED
   Video Port3: DISABLED
   ```

   `snapshot_display -f /data/local/tmp/cursor-audit.jpeg` 返回 `GetDisplayById 18446744073709551615 error!`，未取得截图。用户随后确认此时未接显示器，因此不能把这轮 `No display` 定性为软件缺陷。
5. `usb_host` 的 SIGSEGV 在本轮启动约 246～247 秒时再次出现，最后进入 240 秒延后重启；同轮此前已出现鼠标注册、MMI 打开 event7 和鼠标事件。这说明该服务崩溃没有阻止本次 HID 输入链路走到 MMI；服务自身崩溃仍是另一项待查问题。
6. 参数 `persist.multimodalinput.cursor.hwcbounds` 未设置。因此，依照当前源码中的补丁默认值，预期选择 `SetBounds` 分支；本轮没有核验运行中二进制与构建产物的对应关系，不能仅凭这一参数证明实际执行过哪个绘制分支。

## 原报告的关键代码疑点已解开

复核的源码版本：

- `foundation/graphic/graphic_2d`：`25e62af3936f1e29610b0b1de9a5b0adfa6bf356`，本次 `git status --short` 无改动。
- `foundation/multimodalinput/input`：`5c0f1d08cb7d563778bdba222a7576d9410c0198`，`screen_pointer.cpp` 存在此前的 `MoveSoft` 补丁。

原报告只读了写入端，遗漏了后续消费端。真实链路为：

| 阶段 | 文件与行号 | 实际行为 |
| --- | --- | --- |
| 接口入口 | `foundation/graphic/graphic_2d/rosen/modules/render_service/core/transaction/rs_client_to_render_connection.cpp:612-631` | 若有虚拟屏或 `GetIsPointerEnableHwc()` 为 false，禁止光标跳帧并请求下一次 VSync；随后记录新边界 |
| 暂存 | `foundation/graphic/graphic_2d/rosen/modules/render_service/core/pipeline/rs_pointer_window_manager.cpp:112-123` | 保存节点 ID、位置和尺寸，标记边界更新 |
| 帧内消费 | 同一文件 `:61-109`，关键语句 `:84-89` | `UpdatePointerInfo()` 读取暂存边界，对渲染节点执行 `properties.SetBounds(...)`、`node->SetDirty()`、应用属性和加入待同步列表 |
| 调用时机 | `foundation/graphic/graphic_2d/rosen/modules/render_service/core/pipeline/main_thread/rs_main_thread.cpp:2273-2292` | 在需要遍历节点树的帧中先调用 `UpdatePointerInfo()`，再执行 `rootNode->QuickPrepare(...)` |

因此，“`RSPointerWindowManager::SetHwcNodeBounds()` 本身暂存数据”是局部事实；“不支持硬件光标时不会移动节点”是错误推论。渲染节点的边界更新不受该函数末尾 `UpdateHwcNodeLayerInfo(..., isPointerEnableHwc_)` 的布尔值限制。

这解释了上游非镜像 `MoveSoft()` 只调用 `SetHwcNodeBounds` 的设计。它没有证明所有运行条件下原链路都正常，但已推翻现有补丁注释声称的必然冻结原因。现有补丁仍只能作为未验证的行为变更，不能称作已验证修复。

## 应修正的排查边界

- “没新增 eventN”只能说明预期输入设备尚未注册，仍需区分 USB 枚举、接口/供电、HID 绑定、输入设备注册、evdev 等阶段，不能直接断言唯一原因在 USB 枚举。
- 单独 grep `pointer|mouse` 不证明完整的输入或显示链路。本次通过鼠标名称、usbhid 驱动、MMI 的 event7 fd、事件处理错误和 DRM 状态相互印证。
- 内核源码存在 cursor plane 实现，不等于当前板卡、显示控制器路由和驱动状态已支持可用硬件光标；该能力仍需运行时验证。
- 代码中将合成类型强制为 `COMPOSITION_CLIENT` 的事实，不足以证明历史上“从未验证过光标层”。
- 未接物理鼠标也可以通过受控注入测试部分 MMI/绘制行为，但这种测试不覆盖真实 USB/HID 路径。
