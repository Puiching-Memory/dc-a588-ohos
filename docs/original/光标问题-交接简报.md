七个输入设备全部是按键 / 耳机 / HDMI-CEC，**没有任何鼠标或 HID 指针设备**。

USB 总线树上只有根 hub，无下游设备。三个 dwc3 控制器均已绑定：`fc000000.usb`、`fc400000.usb`、`fcd00000.usb`。

> 排查期间鼠标一直插在操作者的 Windows 主机上，未接到开发板。这是前述误判的直接成因。

### 3.2 `usb_host` 服务崩溃重启循环

```
[246.540138] Child process usb_host(pid 2384) exit with signal : 11
[246.541683] Service warning -1 usb_host, failed to enter sandbox.
```

SIGSEGV，init 每 240 秒重启一次，始终无法进入沙箱。这是独立缺陷。理论上 USB HID 输入由内核 `usbhid` + evdev 完成，不依赖该服务，但若接鼠标后枚举异常，此处为第一嫌疑点。

## 4. 光标链路代码核对结果（全部为读源码得出）

### 4.1 MMI 侧（`foundation/multimodalinput`）

- `ScreenPointer::InitSurface()`：创建 `RSSurfaceNode`，类型 `CURSOR_NODE`，`SetVisible(true)`，`SetFrameGravity(TOP_LEFT)`，`AttachToDisplay(screenId_)`，初始 `SetBounds(0, 0, DEFAULT_CURSOR_SIZE, DEFAULT_CURSOR_SIZE)`。
- 光标像素内容由 `PointerRenderer::Render()` 写入 surface buffer，存在 default / transparent / common 三份 buffer（`InitDefaultBuffer` / `InitTransparentBuffer` / `InitCommonBuffer`）。
- `ScreenPointer::Move()`：硬件光标路径。`CHKPF(hwcMgr_)` 后按屏幕模式计算位置，最终 `hwcMgr_->SetPosition(screenId_, px, py, bh)`。
- `ScreenPointer::MoveSoft()`：软件光标路径。原始实现为 `if (!IsMirror()) SetHwcNodeBounds(nodeId, px, py, DEFAULT_CURSOR_SIZE, DEFAULT_CURSOR_SIZE);`
- `PointerDrawingManager` 中**十余处**以 `GetHardCursorEnabled()` 作为硬件/软件分支的判断条件（行 226/307/380/458/744/780/1313/1345/1384/1423/1462/1540 等）。

### 4.2 能力探测侧

- `HardwareCursorPointerManager::IsSupported()` 调用
  `IDisplayComposerInterface::GetDisplayProperty(devId_, DISPLAY_CAPBILITY_HARDWARE_CURSOR, value)`；
  返回非 `DISPLAY_SUCCESS` 时记 `isDeviceChange_ = true` 并返回 false。
- `HardwareCursorPointerManager::SetPosition()` 调用
  `IDisplayComposerInterface::UpdateHardwareCursor(devId, x, y, buffer)`。
- 枚举定义位于 `drivers/interface/display/composer/v1_2/DisplayComposerType.idl:105`。
- 消费点仅两处：`hardware_cursor_pointer_manager.cpp:78`、`hdi_screen.cpp:295`。

### 4.3 厂商 VDI 侧（`device/soc/rockchip/hardware/display`）

- `display_composer_vdi_impl.cpp:114` — `GetDisplayProperty` 是**无条件桩**，任何属性都返回 `HDF_ERR_NOT_SUPPORT`：

  ```cpp
  int32_t DisplayComposerVdiImpl::GetDisplayProperty(uint32_t devId, uint32_t id, uint64_t& value)
  {
      DISPLAY_LOGE("%s is not supported", __func__);
      return HDF_ERR_NOT_SUPPORT;
  }
  ```

  紧邻的 `GetDisplayCompChange`（同文件 120 行）是正常转发到 `HdiSession::GetInstance().CallDisplayFunction(...)` 的，说明该文件在持续维护，仅此函数从未被填充。

- 该文件 `grep -n "Cursor|cursor"` **无任何匹配**——Rockchip VDI 中不存在任何光标相关方法。
- `UpdateHardwareCursor` 在已构建的 `libdisplay_composer_vdi_impl.z.so` 中**未导出**（`nm -D --defined-only` 无匹配）；全源码树中仅存在于单元测试与 fuzz 用例（`hdi_composer_ut.cpp`、`display_benchmark_test.cpp`、`device_fuzzer.cpp`），**无产品实现**。

### 4.4 RenderService 侧（`foundation/graphic/graphic_2d`）

- `RSPointerWindowManager::SetHwcNodeBounds(int64_t rsNodeId, float x, float y, float z, float w)`
  实现仅做 `SetBound({...})` 与 `SetRsNodeId(rsNodeId)`，再 `SetBoundHasUpdate(true)`，**不移动节点本身**。
- `RSUniRenderVisitor::UpdatePointWindowStatus()`：
  `CheckHardCursorSupport(curScreenNode_)` 结果与 `!isMirrorMode` 相与后 `SetIsPointerEnableHwc(...)`。
- `hdi_screen.cpp:287 GetDisplayPropertyForHardCursor()`：`GetDisplayProperty(screenId, DISPLAY_CAPBILITY_HARDWARE_CURSOR, propertyValue) != DISPLAY_SUCCESS` 或值为 0 时返回 false。

### 4.5 内核侧

光标平面是存在的：`rockchip_drm_vop2.c` 有 `vop2_cursor_plane_init()`，使用 `DRM_PLANE_TYPE_CURSOR`，并支持 `legacy_cursor_update` 异步提交。即：**内核能力具备，缺的是用户态 VDI 的接入**。

### 4.6 厂商合成路径中的可疑代码

`device/soc/rockchip/hardware/display/src/display_device/hdi_gfx_composition.cpp:112-122`：

```cpp
if ((layer->GetCompositionType() == COMPOSITION_VIDEO) ||
    (layer->GetCompositionType() == COMPOSITION_CURSOR)) {
    layer->SetDeviceSelect(layer->GetCompositionType());
} else {
    layer->SetDeviceSelect(defaultCompType);
}
layer->SetDeviceSelect(COMPOSITION_CLIENT);   // ← 无条件覆盖上方所有判断
mCompLayers.push_back(layer);
```

最后一行使上面的分支完全失效。对 GFX 合成而言结果等价（全部走 GPU 客户端合成），但这是明显的调试残留，说明光标层从未在该路径上被真正验证过。

另外 `hdi_drm_composition.cpp`、`drm_display.cpp`、`drm_crtc.cpp` 中 `grep "CURSOR|Cursor"` 也为空——设备合成路径没有任何光标平面绑定逻辑。`drm_plane.cpp:136` 仅把 DRM 属性里的 `DRM_PLANE_TYPE_CURSOR` 解析为 `mType`，没有任何 layer 会被分配给它。

## 5. 已对源码树做的改动

只改了一个文件，其余全部为原始状态。

**文件**：`foundation/multimodalinput/input/service/window_manager/src/screen_pointer.cpp`
**备份**：`/tmp/screen_pointer.cpp.orig`
**函数**：`ScreenPointer::MoveSoft()`

原实现（备份文件 `/tmp/screen_pointer.cpp.orig` 已核实，2026-11-04 09:48，20261 字节）：

```cpp
bool ScreenPointer::MoveSoft(int32_t x, int32_t y)
{
    CHKPF(surfaceNode_);
    if (IsMirror()) {
        CalculateHwcPositionForMirror(x, y);
    }
    int32_t px = x - FOCUS_POINT;
    int32_t py = y - FOCUS_POINT;

    if (!IsMirror()) {
        int64_t nodeId = surfaceNode_->GetId();
        Rosen::RSInterfaces::GetInstance().SetHwcNodeBounds(nodeId, px, py, DEFAULT_CURSOR_SIZE, DEFAULT_CURSOR_SIZE);
    } else {
        surfaceNode_->SetBounds(px, py, DEFAULT_CURSOR_SIZE, DEFAULT_CURSOR_SIZE);
    }
    MMI_HILOGD("Pointer Window SetBounds ScreenId:%{public}" PRIu64
        ", surfaceNodeId=%{public}" PRId64 ", pos=(%{private}d, %{private}d)",
        screenId_, surfaceNode_->GetId(), px, py);
    return true;
}
```

即：原始逻辑中，**镜像模式**走 `SetBounds`，**非镜像模式**只调 `SetHwcNodeBounds`。也就是说上游代码本身认为非镜像场景下 `SetHwcNodeBounds` 足以定位光标——这一点与 §4.4 中「`RSPointerWindowManager::SetHwcNodeBounds` 只记录边界、不移动节点」的读码结论存在冲突。该冲突未查清，是交给专家的一个具体疑点。

修改后：

```cpp
// 显示后端不支持硬件光标时，RSPointerWindowManager 会把 isPointerEnableHwc_ 置为 false，
// 此时 SetHwcNodeBounds 只在渲染侧记录边界，不会移动节点本身。
// 这里默认改用节点自身边界，由常规合成定位；需要回到 HWC 定位时，
// 设置 persist.multimodalinput.cursor.hwcbounds=1 后重启。
static const bool useHwcCursorBounds =
    (OHOS::system::GetParameter("persist.multimodalinput.cursor.hwcbounds", "0") == "1");
if (!IsMirror() && useHwcCursorBounds) {
    int64_t nodeId = surfaceNode_->GetId();
    Rosen::RSInterfaces::GetInstance().SetHwcNodeBounds(nodeId, px, py, DEFAULT_CURSOR_SIZE, DEFAULT_CURSOR_SIZE);
} else {
    surfaceNode_->SetBounds(px, py, DEFAULT_CURSOR_SIZE, DEFAULT_CURSOR_SIZE);
}
```

回退方法：`cp /tmp/screen_pointer.cpp.orig <上面 §9 中的 screen_pointer.cpp 路径>` 覆盖即可。备份若丢失，按上段原始代码恢复 `if (!IsMirror()) { SetHwcNodeBounds } else { SetBounds }` 结构即可。

补充：当前板上的镜像已经包含该改动（`system.img` = `62ae2214…`）。若专家需要未打补丁的基线，须回退源码后重新构建，不能靠参数开关规避——`persist.multimodalinput.cursor.hwcbounds=1` 只能让非镜像分支回到 `SetHwcNodeBounds`，效果上等价于原始行为，可直接用作 A/B 对照，无需重刷。

验证方式：`param get persist.multimodalinput.cursor.hwcbounds` 当前为未设置状态（`GetParameter ... fail! errNum is:106`），因此镜像是走 `SetBounds` 分支运行的。

**该改动没有得到任何有效性验证**——因为从未在接入鼠标的条件下测试过。它修的是一个读代码发现的潜在缺陷，不是已观测到的现象。

其余曾被修改但已完全回退的项：`window_manager_use_sceneboard`（构建参数）、`wms.para` 中的 `multiWindowUIType`。已验证回退后 `build-rk3588.sh` 不含该参数、`wms.para` 中 `multiWindowUIType` 出现次数为 0。

`<dpi>160</dpi>` 保留在 `foundation/window/window_manager/resources/config/other/display_manager_config.xml`，构建产物 `system/etc/window/resources/display_manager_config.xml` 中已确认生效。

## 6. 此前做出的误判（明确列出，避免接手方继承）

1. **「光标冻结在屏幕左上角」不成立。**
   板上从未接过鼠标，该现象从未被真实观察到。左上角存在的某个对象被误认为光标，其真实身份至今未确认。

2. **曾认为切换到 PC / 2in1 形态需要 SceneBoard。错误。**
   经典 `WindowManagerService::LoadWindowParameter()` 读取同名参数即可切换形态，与 SceneBoard 无关。

3. **曾认为自由浮动窗口需要额外开启。错误。**
   `window_node_container.cpp:83` 中 `WindowLayoutMode::CASCADE` 就是默认布局策略。

4. **曾因串口照片判断「无光标」，后又被口头描述改判为「有光标但冻住」，两次都未验证前提。**
   正确做法应先确认 `/proc/bus/input/devices` 是否有指针设备。

5. **对「填 `GetDisplayProperty` 桩即可启用硬件光标」的初始评估严重低估。**
   实际还需要 `UpdateHardwareCursor`（未导出、无实现、底层 DRM 合成也无光标平面绑定），属于子系统级工作量，不是补丁级。

## 7. 待确认的核心问题

1. **左上角那个对象是什么？**
   需要照片或截图。可能是 Launcher 的某个控件、渲染残留、或 bootlogo 区域的伪影。该问题与「鼠标光标」是两件事，需分开定性。

2. **接入 USB 鼠标后，光标是否出现、位置是否正确、移动是否跟手？**
   完全未验证。这是唯一有意义的起点。

3. **`usb_host` 的 SIGSEGV 是否会阻断鼠标枚举？**
   待验证。HID 输入走内核 evdev，理论上不依赖该服务，但该服务持续崩溃本身需要定位。

4. **软件光标在当前实现下能否正常合成？**
   需要确认 `ScreenPointer` 的 surface buffer 是否被正确提交到 RenderService、`CURSOR_NODE` 是否被纳入合成。在无鼠标条件下无法测试。

5. **是否确实需要硬件光标？**
   如果软件光标工作正常，RK3588 上每次移动触发一次局部合成的开销可接受，则不必引入 HWC 光标（其代价见 4.3 / 4.6）。

## 8. 建议的验证步骤

在板上接入 USB 鼠标（接载板 USB-A 主机口）后按序执行：

```sh
# 1. 确认设备已被内核枚举
cat /proc/bus/input/devices | grep -E 'Name=|Handlers='
ls /dev/input/

# 2. 确认 MMI 收到指针事件
hilog | grep -iE 'pointer|cursor|mouse'

# 3. 确认光标参数与分支状态
param get persist.multimodalinput.cursor.hwcbounds   # 期望：未设置 → 走 SetBounds 分支
param get const.product.devicetype                   # 期望：default

# 4. 若 usb_host 仍在崩溃循环，单独取证
dmesg | grep -i usb_host
```

若 `/dev/input/` 中未出现新的 `eventN`，问题在 USB 枚举层，与显示/MMI 无关，应先解决该层再谈光标。
